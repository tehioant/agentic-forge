# Trusted candidate publication (#14)

## Authority and deployment boundary

`publish-candidate` runs **only on the trusted controller host**, under the authenticated operator's OS account. It is not a worker RPC, service, signing oracle, or general GitHub proxy. `--operator-id` does not authenticate anyone. The host integration must authenticate the operator, verify actual approval provenance, and independently inspect controller launch/inspection/check evidence before authoring the private configuration. A worker message, `done`, boolean, reported test pass, assertion of isolation, or `execution_reference` string supplied by a worker is not authorization.

The new private configuration is the operator's exact publication authorization. Its `reference` names the authenticated scope/candidate approval; `execution_reference` names independently verified host execution evidence. Both references must resolve in the operator's trusted records. This code cannot authenticate a conversational message or establish provenance from text. Configuration and SQLite state belong in a private controller-owned directory outside source, all worker profile homes, and all artifact/worker mount trees. Configuration must be a physical regular file, owned by the controller UID, mode `0600`. The artifact envelope must remain controller-owned, mode `0700`. Keep their enclosing directories private as well; a writable parent defeats an OS-file authority boundary. Workers must never run as the trusted host account outside the existing sandbox.

The configuration contains host-only `bearer` authentication for the approved GitHub capability; it is never written into state, CLI output, source, worker prompts, worker environment, or container mounts. Use a repository-scoped GitHub App/fine-grained credential with only the requisite contents/PR permissions and issue metadata reads, not a broad personal account/deployment credential. The adapter supports the exact pinned `https://api.github.com` endpoint or an explicit loopback HTTP capability, and reuses the existing no-redirect/no-proxy HTTP adapter. Endpoint migrations need operator intervention; publication cannot change onboarding or handoff routes.

Existing `sandbox_policy.command` launches the entire worker with `--network none`, a read-only root, non-root identity, dropped capabilities, no new privileges, and a fixed allowlist of mounts and environment. `sandbox_policy.verify` inspects those actual properties and refuses extra mounts/devices/ports. The sole model Unix capability admits the existing model operation, not arbitrary HTTP/GitHub operations. Controller GitHub auth/configuration is not part of that allowlist. Preserve these launch checks; prompts/profiles alone do not deny egress. Deterministic publication tests exercise real loopback HTTP and subprocess CLI; they do **not** establish live Docker enforcement or live GitHub success. Deployment must also exercise the existing actual-container acceptance gate.

## Exact contract

The configuration has exactly these fields:

- `operator_id`, `reference`, `execution_reference`: authenticated operator and independently checked approval/execution provenance.
- `binding`: `factory_v1.publication.binding(persisted_assignment)`, including assignment, claim, stage/profile/role, handoff digest, revision, ticket scope/identity/body, spec/baseline/preceding candidate and full runtime identity. Do not construct it from a worker request.
- `manifest`: host-read source manifest, matching the launcher's `source-artifacts.json`, including every regular file's SHA-256, byte count and executable mode.
- `paths`: the **exact** nonempty approved delta against `inputs/baseline`, at most 200 paths. No prefix globs or repository-wide wildcard. Only those paths enter the Git tree mutation.
- `policy_paths`: exact subset explicitly decided by the authenticated operator. Routine publication holds sensitive paths until this separate operator decision; it is never a worker bypass flag.
- `repository`, `repository_id`, `issue`: exact onboarded repository name/immutable ID and assigned open issue number.
- `branch`, `base`: exact authorized candidate branch and base. First approval assigns this branch; subsequent approvals cannot change branch/repository/base/issue. `main`, `master`, the configured base and the repository's default branch cannot be publication heads.
- `expected_head`: baseline on first publication, or the exact preceding published candidate on updates.
- `candidate`: exact deterministic commit SHA approved after planning.
- `commit_date`: fixed UTC `YYYY-MM-DDTHH:MM:SSZ`. Commit author/committer/message are controller-produced, never worker supplied.
- `api_base`, `bearer`: pinned GitHub capability endpoint and host-only authentication.

Admission requires an active current iteration, held assignment/claim and current spec/ticket pins, a writable implementation/corrections/simplification role, completed controller-observed runtime with container removal, a matching private envelope, and independent operator execution approval. `runtime.status=complete` and `result_disposition.isolated_execution=true` alone do not prove native worker execution or actual installed-skill work. The private authenticated operator configuration independently attests execution only after the host verifies the real records; it must never be derived from worker assertions. Submitted results and `result_disposition.trusted_execution` are deliberately **not promoted**. Repair/diagnostic/review publication, merge, scheduling, integration, checks/protection changes, secret operations and deployment remain unavailable.

Source links/devices and unsafe paths are denied using the existing manifest boundary. Changed files with hardlinks, special permission bits, obvious private-key/GitHub-token content or secret filenames are refused, not operator-overridable. Policy path detection includes workflow/gate/configuration/standards/credential-policy paths, including `lefthook.yml`, `.mise.toml`, `.betterleaks.toml`, hook directories and named security/gate/check tooling under `scripts`, `tools` or `tooling` (see `policy_path` for the explicit list). It does not blanket-ban `factory_v1` security implementation or test changes; these remain independently reviewable. Path detection is not a semantic proof of benign code: independent Standards+Spec review, checks and protection remain later authoritative gates. Do not approve an undetected policy weakening as ordinary implementation.

GitHub Git Data API assembles bounded blobs/tree/commit from host-validated source **without running worker Git, configuration, hooks, or code**. A complete pinned baseline tree is read and each regular baseline file is checked against Git blob/mode identity. Unsupported symlink/gitlink entries and untouched subtrees are preserved, never rewritten or imported as source. Replacement of unsupported entries/ancestors is denied. The candidate uses one exact parent and deterministic controller identity/date/message. Fixed branch updates explicitly use `force: false`; no force/reset/main mutation is exposed.

Pending approval/intent is committed before the first remote object/ref/PR write, with the existing state lock held through readbacks. Publication requires the lifecycle's existing lock file and never creates a replacement lock or SQLite state. Malformed configuration, artifact JSON or stored state is refused with structured stderr and exit 2, without a traceback. JSON reads and source reads remain bounded. Journal candidate/status/PR identity drift and disappearance or reset of a published branch are held, not silently repaired. An identical restart checks the fixed ref/commit and fixed PR target before replay. Lost ref or PR responses reconcile the existing candidate/marker without duplicate PR creation. Pending authorization cannot be replaced; unknown identity, disappearance, replacement, duplicate/closed/merged PR, changed base or unexpected branch are held for the operator. Published updates keep the same draft PR and append one fast-forward commit. Publication uses the stable marker `<!-- factory-v1-publication:ASSIGNMENT_ID -->` and only `Refs #N`, never closing commands. Readback checks commit/tree/parent/message, ref, PR repository ID/name/base/head/candidate/title/body/draft/open status, the PR's issue representation, and the assigned issue remaining unchanged/open. The result is `published`, with `close_allowed: false` and `merge_allowed: false`, never delivered/done.

## Trusted-host live acceptance recipe (parent only)

No live mutation was performed by the implementation worker. The approved target is exactly `tehioant/agentic-forge-fresh-v1-validation`, base/default branch `fresh-spec-validation`. Execute this recipe only after isolated simplification and independent Standards+Spec review, with approved host-only authentication. Do not substitute test-fixture runtime flags for actual launch receipts.

1. Use existing public intake/onboarding/ticket/prepare/launch operations to obtain one current assignment in that exact validation repository. The assigned issue must be an actual open validation-repository issue (its number need not equal product ticket #14). The assignment baseline must equal the current `fresh-spec-validation` SHA. Require actual completed full-process launch, container removal, independent host verification commands, and exact source-manifest evidence. Keep the reviewed source frozen after worker teardown. If earlier prerequisite lifecycle capabilities cannot produce this state, report that integration gate rather than editing SQLite to fabricate it.
2. Set `FACTORY_STATE`, `FACTORY_PROJECT`, `FACTORY_ITERATION`, `FACTORY_OPERATOR`, `FACTORY_ASSIGNMENT`, and `FACTORY_PUBLICATION_CONFIG` to exact approved host paths/IDs; the latter must be outside every source/profile/artifact scope in a private directory. In a trusted host Python process, open state read-only, call `assignments.inspect`, and create the contract above from that **persisted** assignment. Read `manifest(Path(runtime['artifacts']) / 'workspace')`; compare it with `source-artifacts.json`. Compute the exact delta against `inputs/baseline`. Set the exact repository/immutable ID/issue from the inspected assignment; set `base='fresh-spec-validation'`, an operator-selected fresh `branch='factory/validation-14-<unique-approved-run>'`, `expected_head=handoff['baseline']`, and a fixed current approved UTC commit date. Initially use `candidate='0'*40` **only for the read-only plan**. Set `api_base='https://api.github.com'`, matching onboarding and handoff. Enter approved host-only bearer auth through `getpass.getpass()` (not shell arguments or worker environment). Resolve and independently verify `reference`/`execution_reference`; set `policy_paths` only for explicit operator policy decisions. Write JSON via an exclusive `os.open(..., O_WRONLY|O_CREAT|O_EXCL, 0o600)` file in the private directory. Do not print bearer/config contents or store them in evidence.
3. Compute the deterministic plan, with no remote writes:

```bash
python3 -m factory_v1 --state "$FACTORY_STATE" --operator-id "$FACTORY_OPERATOR" \
  publish-candidate --project "$FACTORY_PROJECT" --iteration "$FACTORY_ITERATION" \
  --assignment "$FACTORY_ASSIGNMENT" --publication-config "$FACTORY_PUBLICATION_CONFIG" \
  --plan-only > "$FACTORY_PUBLICATION_CONFIG.plan.json"
```

Inspect the exact planned change paths/tree/candidate and the independent host source verification evidence. The authenticated operator then pins that exact returned `candidate` in the same private configuration and records its candidate-specific approval reference. Planning alone never grants publication; do not publish an unreviewed plan.

4. Genuine publish/readback (only the parent has this capability):

```bash
python3 -m factory_v1 --state "$FACTORY_STATE" --operator-id "$FACTORY_OPERATOR" \
  publish-candidate --project "$FACTORY_PROJECT" --iteration "$FACTORY_ITERATION" \
  --assignment "$FACTORY_ASSIGNMENT" --publication-config "$FACTORY_PUBLICATION_CONFIG" \
  > "$FACTORY_PUBLICATION_CONFIG.receipt.json"
```

Require exit 0, `status=published`, the exact approved candidate, one positive PR number, and both close/merge permissions false. Repeat the same command in a fresh host process and require the same candidate/PR result. Independently read GitHub's exact repository ID, candidate ref/commit/tree/parent, draft PR head/base/repositories/body/marker and associated open issue; retain **actual** responses privately as live evidence without auth headers. Verify `fresh-spec-validation` remained at the baseline and no issue closed. A failed/unknown response is not success: retry the same approved target to reconcile, never create a replacement branch/repository/PR.

5. For a genuine update, produce and independently validate a new bounded source delta in the same assignment, create a new exact operator approval with `expected_head` equal to the published candidate, plan/pin its new candidate, and repeat publication. Require the same branch/PR and a single-parent non-force fast-forward. Deliberately denied role/repo/main/policy/issue/pin cases should use separate private config copies; require no GitHub mutation. Use the deterministic loopback tests for lost-response injection rather than inducing uncontrolled live network failures.

This recipe is an explicit host/operator acceptance gate, not new scheduling or autonomous integration. Later merge/CI/closure gates remain pending and cannot be inferred from publication.

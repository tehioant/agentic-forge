# Conversational handoff (source checkpoint)

The normal interface is the original project conversation: describe the name,
intent, users, objectives, finite milestone, constraints and acceptance. Explicit
existing targets stay literal. Otherwise a new private repository name derives
from the product name under the reviewed account. Product interpretation is not
permission, spending or execution evidence.

The opt-in `project_handoff` plugin setting composes the existing `enrollment`,
`project_setup`, optional `project_creation`, `project_tracker`, `project_execution`
and `onboarding_decisions` configurations. Its fields are `publication_config`
and `wakeup_config`, private absolute host-selected paths (or null to retain an
explicit missing-capability refusal). These are platform settings, not user JSON.
Do not enable a simultaneous static `binding`: there must be one native owner.
This source change does not install or change any Hermes profile.

`ConversationEnrollment.update` retains the correlated product judgment, releases
its draft lock, then calls `ProjectHandoff.advance`. The optional product fields
`repository_mode` (`existing`/`new`) and `repository` preserve the conversation's
choice. Existing targets must occur literally in admitted input. The coordinator
calls the real `ProjectSetup.attach` or `ProjectCreation.create`, then obtains the
real `setup.route` binding. Engineering readiness does not gate native planning.
The original native `sufficient`/`publish`/`complete` schemas and HOST publisher are
reused, with one hook pair and one registered copy of each tool.

After the real native publish tool completes, `after_publication` calls existing
`planning_wakeup.supervise`. That validator separately supports original-turn
completion-before-request and requested-turn completion; only consumed exact
execution/publication authority selects tracker/execution preparation. A queued
message, loaded instruction, external document or returned success string is not
an admitted completion. Native context reconnect also selects this adapter for
already-completed planning. Ticket synthesis/publication and all engineering,
retirement, next-frontier and completion/wait behavior remain in the existing
service/continuation implementation, not another controller.

Blocked setup/create/tracker/execution producers can issue exact retained T6
requests. Status rechecks the fixed producer's host prerequisites; resume calls
only its original public operation. Direction never creates permission. Unknown
producer effects stay held and cannot use setup-only reconciliation as proof for
another producer. Producer-specific verified reconciliation remains unfinished.

## Explicit limitations

This is a tested owned-file checkpoint, not a claim that #72/#68 or conversational
onboarding is complete. The current integrated T5 API still assumes a scoped live
service, real delivery anchor and checkout AGENTS. Fresh provisioning and distinct
preplanning/after-publication phases belong to the concurrent T5 correction.
This coordinator currently calls `execution.register(draft_id, revision)` only;
it must adopt that owner's stable phase API before fresh automatic service
activation can be considered implemented. It does not manufacture those records.

Further source work is needed for dynamic per-project native publisher/wakeup
selection from real host inventory, lifecycle registration of the requested-turn
native subscriber, exact tracker/execution unknown-effect reconciliation and
resolved-decision→next-stage recovery. Those are source integration gaps, not
merely unrun live tests. The retained public continuation component checks prove
their individual contracts, not reachability through a fresh complete project.
No live/native host, GitHub, model, service, worker/container or whole simulated
project journey is performed or claimed. Independent review remains parent-owned.
